# Калорийка — PWA (питание + тренировки)

Дневник питания и тренировок. Чистый HTML/CSS/JS, без сборки, ставится на домашний экран.
Данные — в `localStorage`, при первом запуске создаётся демо-история
(13 дней питания, 6 тренировок, вес за 12 недель).

## Запуск

```bash
node .claude/server.js
```

Дальше http://localhost:4321 — в devtools включить мобильный вьюпорт (iPhone 14 Pro, 393×852).

Открывать файлом (`file://`) нельзя: не зарегистрируется service worker и не заработает камера.

### Установка на телефон

Service worker и manifest требуют HTTPS или localhost. Варианты:

- **По кабелю:** Chrome DevTools → Port forwarding на 4321 (Android).
- **По сети:** отдать localhost наружу туннелем (`cloudflared tunnel --url http://localhost:4321`,
  `ngrok http 4321`) и открыть выданный https-адрес.
- Дальше Safari/Chrome → «Поделиться» → «На экран Домой».

В установленном виде свой статус-бар прячется, отступы под чёлку и home indicator берутся
из `env(safe-area-inset-*)`.

### Разработка и кэш

Service worker работает по стратегии **network-first**: правки видны сразу после обновления
страницы, кэш — только запасной вариант для офлайна. Если что-то залипло:

```bash
# в консоли браузера
navigator.serviceWorker.getRegistrations().then(r=>r.forEach(x=>x.unregister()));caches.keys().then(k=>k.forEach(c=>caches.delete(c)))
```

Офлайн работает после хотя бы одной онлайн-загрузки — раньше кэшу неоткуда взяться.

## Онбординг

Два шага. Первый — параметры и цель. Второй — тренировки: частота в неделю (готовые раскладки на 2–5 дней),
план по дням, отдых между подходами.

- **«Пропустить»** очищает расписание и пускает в приложение. Тренировки включаются потом
  в «Спорт» → «Программы».
- На втором шаге стоит галка **«Оставить демо-историю»**, по умолчанию снятая. Демо-записи полезны,
  чтобы посмотреть на графики, но в реальном дневнике они врут: стрик, процент попаданий и рекорды
  считаются по ним же. Поэтому по умолчанию история стирается.
- Пройти онбординг заново: «Профиль» → «Сбросить всё».

## Поиск продуктов

Подстрочный поиск по-русски не работает: «курица» не находит «Куриная грудка». В `foodMatches()`
лежит лёгкий стеммер — отсекает окончания и сравнивает основы, а если основы разошлись
(«куриц» против «курин»), падает на общий корень в 4 символа. Морфологическая библиотека
для 383 позиций избыточна.

Побочный эффект: редкие ложные срабатывания вроде «голубцы» → «голубика». Терпимо.

Алкоголь: калории есть, а в БЖУ их нет — этанол даёт 7 ккал/г и не относится ни к белкам,
ни к жирам, ни к углеводам. Так считают все трекеры, это не ошибка данных.

## Логика, которую стоит помнить

- **План и факт хранятся раздельно.** У каждого подхода есть `planW/planR` и `w/r`.
  Статусы: `done` (как задумано), `changed` (вес или повторы отличаются от плана), `skipped`.
- **Таймер отдыха считается по timestamp** (`restUntil`), а не по тикам — сворачивание вкладки его не ломает.
  Пауза сессии сдвигает `restUntil` на длительность паузы.
- **Калории тренировки — оценка** по формуле MET × вес × время. Без пульсометра точнее не будет.
- **Вычет тренировки из нормы** — переключатель в профиле. По умолчанию включён, но если дефицит
  уже заложен в норму, это двойной учёт.
- **Распознавание по фото не подключено.** Вкладка «Фото» честно об этом говорит и уводит на штрихкод или поиск.
  Каркас под провайдера готов — см. ниже.
- **Штрихкод — Open Food Facts**, без ключа и лимитов. Покрытие российских товаров неровное:
  если кода нет, приложение предлагает собрать продукт вручную, и он попадёт в «Часто».
  Рядом остался офлайн-драйвер `mock` для тестов.
- **Сканер камерой** — `BarcodeDetector`. Есть в Chrome, **в Safari на iOS его нет** — там ручной ввод цифр.
  Нужен HTTPS или localhost.
- **Программы редактируются.** Шаблоны из `data.js` копируются в состояние при первом запуске,
  дальше живут своей жизнью. Правка программы не трогает уже проведённые тренировки —
  в журнале хранится снимок плана на момент выполнения.
- **Ингредиент бывает двух видов**: ссылка на базу (`{id, g}`) или свой продукт (`{g, custom:{name,kcal,p,f,c}}`).
  Второй нужен для внешних провайдеров, которые вернут продукт, которого у нас нет.

## Распознавание по фото: GigaChat

### Почему нужен прокси

1. Ключ авторизации нельзя отдавать браузеру.
2. Access token живёт 30 минут, его надо обновлять.
3. `api.giga.chat` и `ngw.devices.sberbank.ru` подписаны корнем **Минцифры**, которого нет
   в обычных хранилищах доверия.

Третий пункт решает вопрос хостинга: **Cloudflare Workers, Vercel и Deno Deploy не подходят** —
там нельзя добавить свой корневой сертификат. Нужен процесс, которому его можно передать явно:
локальный Node, VPS или российское облако.

Сертификат лежит в `proxy/russian_trusted_root_ca.cer` и подставляется только для запросов
к Сберу — в системное хранилище ничего не ставится.

### Запуск

```bash
printf '%s' 'ВАШ_AUTHORIZATION_KEY' > ~/.gigachat_key && chmod 600 ~/.gigachat_key
node proxy/server.js
```

Ключ читается из `~/.gigachat_key` или `GIGACHAT_KEY`, в репозиторий не попадает.
Модель задаётся через `GIGACHAT_MODEL`, по умолчанию `GigaChat-2-Max`.

Дев-сервер приложения пробрасывает `/giga/*` на прокси, чтобы всё жило на одном origin.
В профиле приложения адрес прокси — `http://localhost:4321/giga`.

Эндпоинты прокси: `/health`, `/models`, `/recognize`, и `/raw/*` для изучения API (только с локальной машины).

### Как устроен промпт

Каталог продуктов в промпт **не** кладём: 383 позиции — это 3,5 тысячи лишних токенов в каждом
запросе. Модель называет продукты словами, а сопоставляет их с базой `findFoodByName()` —
тот же стеммер, что и в поиске. Совпало — берём выверенные числа из базы; не совпало —
оценку модели, и такой ингредиент помечается в интерфейсе как «оценка».

Экономия проверена: 4923 токена на запрос с каталогом против 1641 без него.

## Подключение провайдера распознавания

Всё живёт в `providers.js`. Экраны про провайдера не знают — меняется одна строка `AI.vision`.

Драйвер обязан вернуть:

```js
{
  dish: "Паста болоньезе",
  emoji: "🍝",
  confidence: 0.82,              // необязательно
  items: [
    { id: "spaghetti", grams: 180 },                             // продукт из нашей базы
    { name: "Соус песто", grams: 30,                             // либо свой
      per100: { kcal: 450, p: 4, f: 45, c: 6 } }
  ]
}
```

**Калории драйвер не возвращает** — их считает приложение по своей базе. Модель ошибается в арифметике, база нет.

Готовые куски:
- `recognitionPrompt()` — общий промпт со списком наших id. Один на всех провайдеров, иначе сравнение
  моделей бессмысленно.
- `parseRecognition(raw)` — принимает строку или объект, вырезает JSON из markdown-обёртки, валидирует,
  отдаёт черновик для экрана правки порции. Бросает `ProviderError` с человекочитаемым текстом.
- В `FOOD_VISION_DRIVERS` лежит закомментированный шаблон `proxy` — фетч на свой бэкенд.

**Ключ провайдера в клиент не кладём.** Нужен прокси (Cloudflare Worker и подобное): он хранит ключ,
у GigaChat ещё и обновляет access token каждые 30 минут, и держит лимит запросов на пользователя.
